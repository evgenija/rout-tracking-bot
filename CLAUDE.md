## Архітектурна перевірка — ПЕРЕД КОЖНОЮ ЗАДАЧЕЮ

> ⛔ Не починаю писати жодного рядка коду поки не відповів на всі питання письмово і не отримав апрув від Жені.

1. **Ізоляція** — новий код не всередині чужого проєкту? Де саме він живе?
2. **Залежності** — не зачіпаю requirements.txt / .env / схему БД без дозволу? Якщо зачіпаю — що саме і чому?
3. **Reusability** — якщо код корисний для P1/P2 — будую як окремий модуль?
4. **Deploy risk** — зміни зачіпають production? Який конкретний механізм шкоди якщо щось піде не так?
5. **IP захист** — бізнес-логіка тільки в services/, не в handlers?
6. **P1 vs P2** — не змішую код двох систем в одній зміні?

## Чек-ліст перед будь-якою зміною коду

### 1. Знайди всіх «сусідів»
```bash
grep -rn "назва_функції\|НазваКласу" . --include="*.py"
```
- Знайди ВСІ місця де використовується функція або клас що змінюється
- Окремо знайди тести де вона мокується або конструюється напряму
- Якщо мок не відповідає новій сигнатурі — оновити мок і пояснити чому

### 2. Перевір формулу числом (якщо є підрахунок або агрегація)
- Побудуй конкретний числовий приклад end-to-end
- Переконайся: значення на вході = значення на виході після агрегації
- Якщо є «сума за діапазон» і «читання по одному дню» — явно перевір що
  читання повертає денне значення (`сума / кількість_днів`), а не суму цілком

### 3. Перевір edge cases для batch/діапазонів дат
- Що трапляється якщо дати не суміжні (є пропуск всередині)?
- Чи є constraint у БД що може заблокувати запис (overlap, unique)?
- Кнопки/дії формуються для кожного суміжного блоку окремо?

### 4. Після кожної зміни — тести і імпорти
```bash
python3 -m pytest tests/unit/ -v --tb=short
python3 -c "import bot.handlers.змінений_модуль; print('OK')"
```
- Якщо тест зламався — виправити і пояснити чому
- Показати git diff перед кожним файлом що змінюється

## Доступ до БД

**P1 SQLite** (`bot.db`) — файл на `worker-volume` Railway. Локальний `bot.db` **завжди порожній** — не читати локально, не аналізувати. Доступ тільки через `railway ssh`.

**P2 PostgreSQL** — Public Networking увімкнено. Запити з локальної машини:
```bash
psql "$DATABASE_PUBLIC_URL" -c "SELECT ..."
```
URL в `.env` як `DATABASE_PUBLIC_URL`. Внутрішній `PG_DATABASE_URL` — тільки з Railway мережі, локально не працює.

Якщо треба проаналізувати дані маршруту — йти одразу в P2 (`daily_input`), не в P1.

## Таблиці P2
- `period_input` — виручка + sales_km; підтримує діапазони (date_from, date_to)
- `daily_input` — дані доставки по водіях
- `coefficients` — коефіцієнти (margin_pct, monthly_shared, monthly_taxes, revenue_median_2025 та ін.)

## P2 daily_input — перевірка дублів (для аналізу старих даних)
`on_route_finished()` з 01.05.2026 ідемпотентний: SELECT перед INSERT, при continuation → UPDATE.
Для аналізу даних **до** цього фіксу — перевіряти дублі:
```sql
SELECT route_id, COUNT(*), SUM(km), SUM(logistics_cost)
FROM daily_input
GROUP BY route_id HAVING COUNT(*) > 1;
```
Якщо дублі є — злити вручну в один запис з правильним km і тарифом.

## P1 continuation mechanism — правила
- 1 маршрут на день на водія — бізнес-правило, не технічне обмеження
- `cmd_start_route`: якщо сьогодні є завершений маршрут → показати кнопку «▶️ Продовжити маршрут #N», НЕ реактивувати автоматично
- `reactivate_route()` викликати тільки з `callback_continue_route` після натискання кнопки
- При змінах у `cmd_start_route` — явно перевіряти `get_todays_finished_route()` і continuation flow
- `get_route_waypoints_from_last_start()` повертає km тільки від останнього «Старт» маркера — km другого сегменту незалежний від першого
